# Matahari 第一间学校交付研究

研究日期：2026-09-06。代码基线：`64b796f`。

本文是基于本地代码、接口、模型和现有测试的交付研究与建议顺序，不代表以下功能已实现，也不是整套功能的实施规格。本轮没有重新运行测试、操作真实学校数据或复核商店最新条款。现有基线的完整 GitHub 验证已通过：[run 34016761118](https://github.com/Kaikaiyng/Matahari/actions/runs/34016761118)。

## 交付目标

学校能自行建立学生、家长、员工、学年和分班资料，完成收费与核对；老师和家长能通过各自账号看到正确范围的数据；正式环境具备备份和支持安排。对外交付同时包括 Admin 网页与 Android/iOS School App。内部开发和测试分批推进，不把 Android 内测完成等同于双平台交付。

RYLAY SaaS、架构重写、AI Quiz 和复杂自动化继续延后。现有 Matahari dedicated 模式、PostgreSQL、权限和历史数据结构作为基础。

## 已核实的依赖

| 依赖 | 代码证据 | 对交付的影响 |
| --- | --- | --- |
| 家长资料与账号分开 | [Guardian](../backend/app/Models/Guardian.php) 使用 `parents`；可空 `user_id` 指向登录账号 | 新增联系人不能等同于开通 App |
| 关系与可见权限分开 | [StudentParentLink](../backend/app/Models/StudentParentLink.php) 保存关系、状态、财务/学业权限与日期 | 一位家长的多个孩子需要分别审核权限 |
| 激活要求明确关联账号 | [PortalLinkService](../backend/app/Services/Foundation/PortalLinkService.php) 和 [现有测试](../backend/tests/Feature/PhaseAFoundationApiTest.php) 拒绝跨校关联及未关联账号的激活 | 不通过姓名、电话或邮箱自动匹配身份；不默认激活历史关系 |
| 家长目录仍是示例数据 | [ParentsPage](../frontend/src/components/ParentsPage.tsx) 的家长与孩子来自 `DEMO_PARENTS`，仅班级列表调用 API | 页面看起来完整，实际不能作为学校的家长名册 |
| 普通资料班级与学年分班独立 | [ClassEnrolmentService](../backend/app/Services/Foundation/ClassEnrolmentService.php) 保存学年分班历史；学生资料编辑只修改 `students.class_id` | 改资料班级不能让老师自动获得新学年考勤名单 |
| 教务写接口已有，后台入口不完整 | [API routes](../backend/routes/api.php) 有学年、科目、分班、任教分配接口；[ClassesPage](../frontend/src/components/ClassesPage.tsx) 主要是目录、名单和考勤 | 必须补齐学校自己建立与维护教务基础资料的流程 |
| 家长财务依赖确认的当前分班 | [Business Rules](business-rules.md) 规定从当前 enrolment 获取学年，金额来自现有账目 | 不能靠页面硬编码学年解决家长看不到金额的问题 |
| 导入只覆盖新增学生 | [Student CSV Import](student-csv-import.md) 不写家长、账号、学年历史或财务 | 真实 Excel 接入需要分阶段校验与对账 |

权限以 [Permissions](permissions.md)、当前权限解析器和服务端校验为准。不要套用旧文档中按 Finance 等职位名称一概允许或拒绝的描述。

## 分批推进建议

每批以一个能单独使用、验收的结果为边界。下表是建议，不是已完成状态或时间承诺。

| 批次 | 可交付结果 | 完成判断 |
| --- | --- | --- |
| 1. 真实家长目录 | Parents 页面读取同校家长与已存孩子关系，支持搜索、分页及状态展示 | 无示例数据回退；空、失败、无权限状态准确；不可越校读取 |
| 2. 家长资料维护 | 新增/编辑联系方式与备注，建立明确的家长—学生关系 | 保存可回读、有事务审计；历史关系保留；资料维护不会自动开通 App |
| 3. 账号与访问 | 开户、选择/关联现有账号、按孩子开通或结束访问，再补停用和密码恢复 | 用虚构家庭走通“建资料→关联→登录→只看自己的孩子→撤销即失去访问”；账号管理有服务端保护与审计 |
| 4. 教务建立 | 学年、科目、学生分班与结束分班、教师任教分配的管理入口 | 管理员能建立一个学年；老师拿到正确名单；历史记录不被覆盖 |
| 5. 财务与 Excel 试迁移 | 根据学校真实规则完成必需折扣/特殊账务、导入映射与期初对账 | 学生/家庭数量、每生欠款及汇总均与确认的来源一致；没有重复收费或伪造历史收据 |
| 6. 最少报表 | 按学校结账需要选择首发报表，例如期间收款、欠费清单、学生对账单 | 页面、导出和来源账目在同一口径下可核对 |
| 7. 交付准备 | 测试环境、原生登录/包装/推送、真机试用、支持与发布资料 | Admin 与两个平台完成目标角色流程；备份恢复、正式部署和上架证据分别齐备 |

部署和原生可行性准备不必等第 6 批全部结束。家庭与教务的最小流程稳定后，可安排小范围测试环境和原生登录验证，提前发现手机、签名和账号归属问题；功能上线仍按验收结果控制。

## 下一批只做：真实家长目录

建议先交付只读目录，作为后续资料维护、孩子关联和账号管理的入口。现有表已能提供目录基础，本批预计不需要新表；实际实施前仍须核对查询与历史关系语义。

涉及位置：

- 新增同校家长目录 Controller/查询与对应 Feature 测试；接入 `backend/routes/api.php` 的 Admin、认证、学校上下文和 `parents.view` 权限链。
- 复用 `Guardian`、`StudentParentLink` 与已验证的学校范围，返回允许展示的资料，不返回账号凭据。
- 更新 `frontend/src/components/ParentsPage.tsx` 和对应测试；复用现有 Admin 控件，移除 `DEMO_PARENTS` 回退。
- 更新 `docs/current-status.md`、`docs/project-overview.md` 与 `docs/UAT_CHECKLIST.md`。

验收情境：

- [ ] 只显示当前学校的家长；同校与异校同名资料不会混入结果。
- [ ] 一个家长关联两个孩子，两个家长关联同一个孩子，均能准确展示。
- [ ] 未关联账号、未审核关系及已结束关系有准确标识；“列出关系”不授予 App 权限。
- [ ] 未授权请求由后端拒绝；没有学生查看权限时，不通过目录绕过学生资料可见范围，具体展示范围在该批实施规格中明确。
- [ ] 搜索、分页和统计口径一致；空库显示空状态，API 失败显示错误及重试，不显示示例家庭。
- [ ] 用虚构数据验证后端学校/权限边界及前端状态；执行受影响完整测试，数据库查询在 PostgreSQL 验证。只读实现不新增虚构写入审计。

本批结束后再细化第 2 批的字段、关系生命周期和事务边界，不一次生成整套账号或财务系统。

## 到相应阶段才需要的资料

| 阶段 | 需要的真实信息 | 没有这些信息时仍可推进的工作 |
| --- | --- | --- |
| Excel 映射 | 脱敏样表、字段含义、学生编号规则、家庭关系、计划切换日期 | 使用虚构资料完成目录、表单、验证与导入预检 |
| 财务规则 | 实际折扣例子、旧欠款口径、是否存在预收/押金/退款、收款核对方式 | 完善已批准的正常收费收据流程；不猜公式和期初金额 |
| 教务数据 | 正式学年起止日期、班级名单、教师任教安排 | 完善管理入口；不自动把示例学年变成生产学年 |
| 部署/商店 | 学校正式域名、服务器及账号归属、发布主体、开发者账号、支持负责人 | 整理环境配置、构建流程和测试清单；不把占位联系人当成真实支持 |

真实 Excel、凭据、家庭资料和财务记录放在受控私有位置，不进入 Git 或本文件。暂时不要求学校一次性提供所有资料。
